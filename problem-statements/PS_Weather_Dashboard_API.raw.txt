Weather Dashboard Microservice

Build a backend microservice that provides current weather data, 5-day forecasts, temperature unit conversion, configurable severe weather alerts, and user favorites, all powered by a bundled mock weather dataset with no external API key required.

Scenario: A smart-campus initiative needs a weather dashboard backend. The service must aggregate weather information for multiple cities, let users set alert thresholds for dangerous conditions, and cache results in SQLite to minimize redundant lookups. A mock weather provider with data for 25 cities is included so the service runs fully offline.

Technology stack:
- Python 3.12+
- Flask
- SQLite
- SQLAlchemy
- requests (mock provider)
- pytest

Functional requirements:

FR-1 Get Current Weather
Retrieve current weather by city name or latitude/longitude coordinates. The response should include temperature, humidity, wind speed, and condition, and it should support a units parameter for celsius, fahrenheit, or kelvin.

FR-2 Get 5-Day Forecast
Return a 5-day forecast with daily summaries including high temperature, low temperature, dominant condition, and hourly breakdowns.

FR-3 Temperature Conversion
Convert temperature values between Celsius, Fahrenheit, and Kelvin. The API must support single conversion through GET and batch conversion through POST, covering all six directional pairs.

FR-4 Severe Weather Alerts
Allow users to configure alert thresholds and check current conditions against them. Thresholds should support temp_high, temp_low, wind_speed, and humidity, and severity should be classified as warning or critical.

FR-5 Weather Data Caching
Cache weather responses in SQLite with a configurable TTL and expose cache statistics. Cache keys should be based on city plus data type, hit and miss counts should be tracked, and there should be a cache-clear endpoint.

FR-6 Favorites and History
Let users save favorite cities and automatically track search history. The API should support adding, listing, and removing favorites per user, and search history should record city, search type, and timestamp.

API endpoints:
- GET /api/weather/current: Get current weather by city or coordinates. Success: 200. Errors: 400, 404.
- GET /api/weather/forecast: Get a 5-day forecast for a city. Success: 200. Errors: 400, 404.
- GET /api/weather/convert: Perform a single temperature conversion. Success: 200. Errors: 400, 422.
- POST /api/weather/convert: Perform batch temperature conversion. Success: 200. Errors: 400, 422.
- GET /api/cache/stats: Get cache hit/miss statistics. Success: 200.
- DELETE /api/cache: Clear all cached weather data. Success: 200.
- POST /api/alerts/configure: Set or update alert thresholds for a user. Success: 200. Errors: 400, 422.
- GET /api/alerts/check: Check current conditions against configured alerts. Success: 200. Errors: 400, 404.
- POST /api/favorites: Add a city to a user's favorites. Success: 201. Errors: 400, 409.
- GET /api/favorites: List a user's favorite cities. Success: 200.
- DELETE /api/favorites/{city}: Remove a city from favorites. Success: 200. Errors: 404.
- GET /api/history: Retrieve a user's search history. Success: 200.

Data model:

WeatherCache
- cache_key: string, primary key, formed from city_name and data_type
- city_name: string, city associated with cached data
- data_type: string, current or forecast
- data: JSON, cached weather response payload
- fetched_at: datetime, when the data was originally fetched
- expires_at: datetime, cache expiration time

Favorite
- user_id: string, identifies the user
- city_name: string, favorite city name
- Unique constraint on (user_id, city_name)

SearchHistory
- user_id: string, identifies the user
- city_name: string, city that was searched
- search_type: string, current or forecast
- searched_at: datetime, auto-set on creation

AlertConfig
- user_id: string, primary key, identifies the user
- temp_high: float, threshold for high temperature alert, optional
- temp_low: float, threshold for low temperature alert, optional
- wind_speed: float, threshold for wind speed alert, optional
- humidity: float, threshold for humidity alert, optional

Alert severity rules:
- When a current reading exceeds a threshold by less than 20%, severity is warning.
- When it exceeds by 20% or more, severity is critical.

Mock weather provider:
The service includes a built-in mock weather data provider with a JSON dataset covering 25 cities worldwide. The provider should return realistic weather data including temperature, humidity, wind speed, and conditions such as sunny, cloudy, rainy, and snowy.

Success criteria:
- All 12 endpoints return correct status codes and response structures.
- Weather queries by city name and by coordinates both work correctly.
- Temperature conversions are accurate across all six directional pairs.
- Cache stores responses and serves them on subsequent requests within the TTL window.
- Cache statistics accurately reflect hit and miss counts.
- Alert configuration persists per user and the check endpoint evaluates current conditions against thresholds.
- Favorites and search history are correctly scoped per user.
- The application starts cleanly with no external API keys required.
